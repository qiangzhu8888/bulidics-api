# BULIDICS HTTP Push API v1.0

## Scope and direction

BULIDICS sends collected device data to an HTTP endpoint provided by the customer. The flow is one-way:

`Device -> BULIDICS -> customer data integration API`

The customer does not poll BULIDICS for this interface.

## Transport

| Item | Current specification |
|---|---|
| Method | `POST` |
| Protocol | HTTP or HTTPS; HTTPS is recommended |
| Content-Type | `application/json` |
| Character encoding | UTF-8 |
| Destination | Customer-provided internet-reachable HTTP(S) endpoint |
| Source IP | Fixed source IP is supported; customer-side allowlisting is possible |
| Authentication | No API Key or Bearer Token is defined in v1.0 |

`User-Agent`, `Host`, `Accept`, `Connection`, and `Content-Length` are generated by the HTTP client and are not customer implementation requirements.

## Payload model

The request body is a flat JSON object. Each key identifies a device measurement point and each value is the measurement value.

Field name pattern:

```text
{deviceId}_{measurementIdentifier}
```

Treat `deviceId` as a string even when it contains only digits.

### Supported examples

L5 temperature/humidity sensor:

```json
{
  "1000001_temp": 25.0,
  "1000001_hum": 20.2
}
```

- `{deviceId}_temp`: number; floating-point temperature
- `{deviceId}_hum`: number; floating-point humidity

L5 water-leak sensor:

```json
{
  "EFF4B9936179_waterLeak": 0
}
```

- `{deviceId}_waterLeak`: number; `0` = normal, `1` = leak detected

Field combinations depend on device type. Implementations should iterate over received fields and tolerate unknown fields rather than hard-coding one payload shape.

## Response and success criteria

- Return HTTP `200` after successful receipt. The response body is not specified and may be empty.
- BULIDICS treats any HTTP `2xx` as delivery success.
- A non-`2xx` response or timeout is a delivery failure and triggers retry.
- Respond quickly. Queue or buffer the payload and perform heavy processing asynchronously when appropriate.

## Timeouts and retry

| Item | Value |
|---|---|
| Connection timeout | 15 seconds |
| Response timeout | 60 seconds |
| Maximum retries | 3 |
| Retry delays | first: 2 seconds; second: 4 seconds; third: 6 seconds |
| After retry limit | Record an error log and finish |

Retries can deliver the same payload multiple times. Customer processing should be idempotent. The current payload does not contain a specification-defined deduplication key.

## Customer readiness checklist

- Accept `POST` and `application/json`.
- Parse a UTF-8 flat JSON object.
- Treat device IDs as strings.
- Return HTTP `200` after successful receipt.
- Handle non-`2xx` and timeout-driven redelivery.
- Avoid business impact from duplicate delivery.
- Tolerate unknown measurement fields.
- Test with both a simulated request and actual BULIDICS device data.
- Log the request headers, full body, and occurrence time when investigating discrepancies.

## Future candidates — not current v1.0 requirements

The following are proposals only. Do not include them in current implementation examples unless the user explicitly asks for a future specification:

- API Key or Bearer Token for push authentication
- `timestamp` to distinguish measurement time from receipt time
- `messageId` for easier duplicate detection
- structured JSON separating `deviceId`, `deviceType`, and `data`
- explicit event, periodic, and state-change delivery modes
- status-specific retry policy for 4xx, 5xx, 408, and 429
- additional leak states beyond `0` and `1`
